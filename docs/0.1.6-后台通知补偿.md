# 0.1.6：后台通知补偿接收

## 实机结论

2026-10-19 已在用户的红米 K90 Pro Max（Android 17）＋小米 AI 眼镜上完成桌面新微信自动播报，以及息屏连续两条新微信自动播报，用户确认实际听到，未点击媒体播放。此次锁屏失败的直接证据是 HyperOS Greeze 冻结进程；完成听讯专属后台策略重设、自启动与通知监听重新绑定后，息屏回调、合成、焦点、蓝牙路由和播放均连续完成。手机保留即时朗读、原 9 个应用和 AI 语音配置，听读会话继续开启。

补偿扫描是额外容错，不能对抗已经冻结的进程，也不能把这次实机恢复单独归功于扫描。长期静置、拔掉 USB 后的续航运行、重启后手动开启、通话/断连等本轮未全部实测，不能将本次两条消息验收扩展为所有运行条件的保证。

## 证据与边界

2026-10-19，用户反馈 0.1.5 前后台均无声音，重启眼镜后前台恢复，后台仍不即时朗读。用户确认系统通知栏出现新微信通知、听讯选择即时朗读。

提供的诊断包含多次云端/系统合成、焦点获准、蓝牙 A2DP 路由确认和播放器完成，但没有新通知接收、入库及自动调度事件。它不能证明人耳实际听到，也不能证明系统没有送达回调：0.1.5 在记录前已做应用、时间和通知类型过滤。本次不把“耳机重启恢复”归因于代码修复，不宣称已确定红米后台问题的根因。

## 修改

- 用户开启的前台会话每 2 秒调用已授权通知监听服务的 `getActiveNotifications()`，独立于 Activity 和媒体播放按钮，补偿可能延迟或缺失的回调。系统回调仍直接触发即时处理。
- 只检查所选应用，保留会话开启时间、持续状态、分组摘要、会话消息时间等过滤。未开启会话时不扫描；扫描不绕过系统的敏感通知限制。
- 内存最多保存 256 项通知变化指纹，未变化的活动通知不反复入库。正文变化但 postTime 相同也能发现。Room 仍承担持久化去重，回调迟到、缓存淘汰及扫描重复不能重复朗读。原有暂停、清空、断连与旧积压确认规则保留。
- 增加 `NOTICE_RECOVERED`、`NOTICE_FILTERED`、`LISTENER_QUERY_FAILED`。诊断头附当前模式、语音引擎、已选应用数量、监听状态及当前进程的回调/过滤/扫描计数。过滤事件的 value 对应 CaptureSignal 的固定枚举序号，不包含应用包名、联系人、正文或密钥；事件仍限 200 条/24 小时，计数仅为本进程内存统计。
- 不修改已有应用选择、免打扰、MiniMax/OpenAI 配置或授权，不更改生产耳机输出安全检查，不加全天唤醒锁。
- 首页首屏显示实际内容模式与语音引擎，混合模式明确说明普通消息按间隔总结。听读服务支持 Android 既有的 `dumpsys activity service cn.tingxun.app/.ListeningService` 导出同一份匿名诊断；没有新增导出广播组件，不访问密钥或原通知文件。

扫描只能发现系统仍保留的活动通知，通知在扫描前被移除时无法补收。2 秒是会话内目标核对周期；系统休眠、厂商冻结、通知本身送达延迟及合成耗时仍可能增加实际出声延迟。

## 验证与安装

新增指纹变化/缓存边界单元测试，以及锁屏漏回调补偿仪器测试：模拟只有活动快照、没有系统回调；验证新消息自动处理、旧消息和状态通知排除、重复扫描与迟到回调去重、同时间戳正文更新、清空后不复播。该用例模拟的是漏回调条件，最终输出使用测试替身，不证明红米眼镜出声；原有真实 TTS、焦点、MediaPlayer 和 Android 17 严格音频限制测试继续保留。

同签名 0.1.6，versionCode 7，compile/targetSdk 36，Android 11 起支持。覆盖安装，连接眼镜，保持“即时朗读”，开启一次听读后退到桌面或锁屏，由另一设备发送新微信消息，第一条前不点试听或媒体播放键。

本轮已通过 USB 连接红米 Android 17＋小米 AI 眼镜。0.1.5 的实际页面为混合模式、5 分钟，已按用户要求切成即时朗读；用户反馈切换后的后台试验仍无声音，不能据此认定仅修改模式已解决。系统媒体前台服务和通知监听绑定存在，后台网络规则 effective=NONE；这些状态不能单独证明消息已自动处理。

已正常覆盖安装 0.1.6，原 9 个应用及 AI 语音配置保留，确认当前即时朗读＋AI 合成语音，前台开启会话后回桌面。匿名 USB 诊断可读，活动通知核对计数增长。

实机桌面试验：用户发送全新微信并确认眼镜自动读出，没有点击媒体播放或打开听讯。对应记录为 `NOTICE_RECEIVED → NOTICE_STORED(id=100) → AUTO_DISPATCH → CLOUD_BEGIN / DONE → FOCUS_RESULT(1) → ROUTE_CONFIRMED(8/A2DP) → PLAY_DONE`，进程 importance=125、UI 不可见。回调至路由确认约 1.21 秒（这是软件阶段计时，不是人工测得的耳机出声延迟）。该条走正常回调而非 NOTICE_RECOVERED，不能据此认定旧版根因就是丢回调。匿名记录见 `results/0.1.6/redmi-desktop.json`。

首次锁屏连续两条试验失败。实机匿名记录显示屏幕关闭后，核对计数和心跳停止，两条通知直到开屏才一并送达；系统日志明确记录锁屏约 1 秒后 `GreezeManager FZ uid=10311 reason=AUDIO_APP`、`freezeUid SUCCESS ... cn.tingxun.app`，开屏后 `THAW ... reason=screen_on`。这确认了该次失败属于 HyperOS 进程冻结，而非合成或焦点阶段受阻；2 秒补偿扫描无法在被冻结的进程内运行。记录见 `redmi-lock-failure.json` 与 `redmi-freeze-policy.txt`。

应用省电页原本显示“无限制”，重新保存该选项后系统策略日志出现 `NO_RESTRICT_APP`；并开启听讯的自启动。策略调整过程中原进程退出，通知监听曾被 AutoStartManagerService 拒绝重绑，因此刷新听讯原有通知访问授权，重新开启用户会话。未关闭全局冻结机制，未使用 root 或静音保活；应用仍只在合成/播放期间限时持有唤醒锁。

再次息屏实测通过：两条全新微信的 id 为 104、105，均在 `screenOn=false` 时接收、入库和 AUTO_DISPATCH，分别取得焦点、确认 A2DP 路由并 PLAY_DONE；第二条在第一条播放期间到达，随后自动继续播放。用户确认“两条都自动读出了”。第一条回调至路由确认约 6.06 秒（含云端合成 5.80 秒）；第二条等待前一段播放，约 5.96 秒后确认路由。全过程没有亮屏或媒体播放指令，最终系统 Wakefulness=Dozing。匿名记录见 `redmi-lock-success.json`。

验证结果保存在 `results/0.1.6/`。

54 项单元测试、Android 15 / API 35 与 Android 17 / API 37 各 22 项设备测试通过，0 失败、0 跳过。API 37 的真实 TTS＋焦点＋MediaPlayer 首次自动播放测试确认 hardening override=3；四种后台场景（共 8 条通知）均不调用媒体播放按钮。首页模式提示另通过 API 35 四页面 UI 回归。Lint 无错误；0.1.5 → 0.1.6 同签名覆盖升级和冷启动通过。
